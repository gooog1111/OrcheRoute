# Функциональный контракт Android и Server

Этот документ фиксирует пользовательское поведение OrcheRoute Android 0.5.10 и
его перенос в серверную версию. Общие правила должны реализовываться в Go-слоях;
Android и Server содержат только платформенные адаптеры.

Статусы в таблицах:

- **единое** — используется общий Go-код или одинаковый API-контракт;
- **реализовано** — серверный эквивалент работает;
- **переносится** — общий слой существует, но серверный lifecycle ещё не завершён;
- **платформенное** — буквальный перенос не нужен, используется эквивалент ОС.

## 1. Lifecycle и состояние

| Возможность Android | Серверный эквивалент | Статус |
|---|---|---|
| Явное включение и выключение VPN | Управление systemd/Windows Service и Mihomo | реализовано |
| Сохранение намерения «VPN включён» | Состояние в `state.db`, автозапуск системных служб | реализовано |
| Восстановление после перезагрузки | Enable/disable системных служб | реализовано |
| `VpnService` и системный значок ключа | TUN Mihomo и системная служба | платформенное |
| Foreground-уведомление с трафиком | WebUI/API, журнал и метрики службы | платформенное |
| Локальный WebView без авторизации | WebUI с авторизацией; loopback Desktop без неё | платформенное |

Чистая установка не должна включать VPN автоматически. Настройки, подписки,
маршруты и серверы сохраняются при остановке, ошибках проверки и обновлении.

## 2. Независимый монитор физической сети

Монитор не зависит от состояния Mihomo и возвращает только:

- `normal` — подтверждён обычный открытый интернет;
- `allowlist` — отвечает хотя бы один доступный ресурс, но открытый интернет не
  подтверждён;
- `offline` — не отвечает ни одна контрольная точка.

Android привязывает DNS и HTTP к физическому `Network`. Server обязан привязывать
DNS и HTTP к интерфейсу роли `direct`, обходя TUN и системный маршрут VPN.
Контроллер, failover и whitelist-сканирование только читают последний
подтверждённый снимок. Они не запускают собственные конкурирующие проверки.

Переход `normal ↔ allowlist` подтверждается двумя наблюдениями, переход из
рабочего состояния в `offline` — тремя, восстановление из `offline` — одним.
URL обычного интернета и URL, доступный при белых списках, настраиваются в
политике квалификации.

| Android | Server | Статус |
|---|---|---|
| `ConnectivityMonitor` + общий классификатор | Фоновый монитор bound к `direct` | единое |
| Автовосстановление VPN после появления сети | Контроллер системной службы | реализовано |
| Пауза VPN при `offline` без сброса намерения | Остановка transport с сохранением `enabled` | реализовано |

## 3. Подписки и серверы

Поддерживается единый автоматический парсер. Пользователь не выбирает тип
подписки вручную. BlackTemple определяется только успешным ответом специального
протокола, а не именем, доменом или подписью.

Общий контракт:

- создание, изменение, включение и удаление источника не запускают обновление;
- обновление одной или всех подписок выполняется отдельно;
- проверка одной или всех подписок использует сохранённые ссылки без загрузки;
- неуспешная загрузка не стирает прежние ссылки и серверы;
- успешная непустая загрузка заменяет кэш подписки;
- дубли подписок и серверов исключаются;
- поддерживаются URL, share-ссылки, текстовый список, файл и пакетный импорт;
- секрет и готовые серверы можно экспортировать через доверенный локальный API;
- EbraSha и Au1rxx доступны как отключаемые встроенные аварийные источники;
- название пользовательского источника необязательно;
- удаление сервера из списка действует до следующей проверки или обновления.

| Возможность | Server | Статус |
|---|---|---|
| CRUD, импорт, экспорт, встроенные источники | API и SQLite | единое |
| Обновить/проверить одну или все подписки | Go updater | единое |
| Сохранение старого кэша при ошибке | Go updater | единое |
| Удаление отдельного сервера из снимка | API и provider-файл | реализовано |
| QR и Android document picker | Загрузка файла/буфера через браузер | платформенное |

## 4. Квалификация и рейтинг

Последовательность проверки:

1. TCP-проверка;
2. URL-test по настраиваемому списку HTTPS-адресов;
3. при включённом фильтре — геолокация и исключение стран;
4. два speed-test, если тестовый файл доступен;
5. проверка минимальной скорости и стабильности;
6. сохранение рабочего набора без уничтожения предыдущего при ошибке.

Таймауты, количество кандидатов, число сохраняемых серверов, исключённые страны,
минимальная скорость и коэффициент стабильности настраиваются. Для аварийных
источников до speed-test берётся заданное количество лучших URL-test результатов
из каждого источника. Порог скорости равен 10% измеренной прямой скорости либо
пользовательскому значению, если baseline получить нельзя.

Рейтинг: ping 40%, скорость 35%, стабильность 25%. Отсутствующая скорость
нейтральна. Автоматический режим всегда предпочитает основной список, даже если
аварийный сервер имеет более высокий балл.

| Возможность | Server | Статус |
|---|---|---|
| TCP → URL → geo → speed → stability | Go qualification backend | единое |
| Прогресс с точными `current/total` | operation API | реализовано |
| Общий рейтинг при выборе активного узла | `noderank` в server controller | единое |

## 5. Режимы управления

- **Автоматически:** основной список, затем аварийный; активный узел удерживается
  до подтверждённого отказа.
- **Ручной режим:** выбранный сервер закреплён до возврата в автоматический.
- При работе на аварийном сервере основной список периодически обновляется и
  проверяется; возврат выполняется только на подтверждённый основной сервер.
- Отдельная пользовательская настройка «только аварийный список» отсутствует.

Server должен хранить дату и время последнего переключения и не запускать вторую
операцию обновления, пока первая активна.

## 6. Белые списки оператора

При подтверждённом `allowlist` используется отдельный устойчивый список:

- проверяются все сохранённые серверы всех включённых источников;
- региональные исключения временно не применяются;
- пользовательские маршруты временно заменяются на `proxy` для всего, кроме
  `block` и обязательного локального bypass;
- старый рабочий whitelist-список не очищается до готовности замены источника;
- проверка не останавливается после первого рабочего сервера;
- VPN не запускается из частично сформированного списка, чтобы оставшиеся тесты
  продолжали идти через тот же физический интерфейс;
- после отказа узел удаляется из whitelist-списка и выбирается следующий;
- при пустом списке transport останавливается, намерение пользователя остаётся,
  повтор выполняется не чаще одного раза в пять минут;
- операцию можно остановить; завершённые результаты сохраняются;
- проверку можно запустить для всех или одной подписки;
- после готовности списка подписки обновляются последовательно, а изменившиеся
  наборы проверяются повторно.

| Возможность | Server | Статус |
|---|---|---|
| Переносимая модель whitelist-списка | `internal/whitelist` | единое |
| Полное формирование и повтор через 5 минут | Server orchestration | реализовано |
| Отмена операции | Кооперативная отмена updater | реализовано |
| Проверка одной подписки в `allowlist` | API + updater | реализовано |

Server использует отдельный Mihomo provider `whitelist`. Начальное формирование
работает только по сохранённому кэшу и не включает transport до завершения всех
выбранных источников. После подключения подписки обновляются последовательно;
повторно квалифицируются только источники, чей кэш действительно изменился.

## 7. Маршрутизация

Действия: `direct`, `proxy`, `block`. Поддерживаются:

- отдельный IP, CIDR и диапазон IP;
- точный домен, суффикс и маски (`*.ru`, `*yandex.ru`);
- `geoip:*` и `geosite:*`;
- TCP/UDP и готовые типы трафика;
- порт `:5000`, диапазон `:5000-6000`, список `:5000,5002,5005`;
- настраиваемое действие по умолчанию.

Правила валидируются и компилируются до сохранения. При остановленном Mihomo они
должны сохраняться и применяться при следующем запуске. Server дополнительно
привязывает `direct`, VPN underlay и management bypass к выбранным интерфейсам.

Статус Server: **единое**, включая сохранение маршрутов при остановленном core.

## 8. DNS и сетевой профиль

Общий профиль содержит роли `direct`, `proxy`, `vpn_underlay`, интерфейсы,
режим системного захвата, локальные и management CIDR, IPv6 и DNS для direct,
proxy, underlay и bootstrap. Обычные DNS-запросы проходят через Mihomo и правила;
локальные сети и loopback не должны зацикливаться в VPN.

Android применяет профиль через `VpnService`; Server — транзакционным сетевым
helper и системными маршрутами с откатом. Статус Server: **реализовано**.

## 9. GeoIP, GeoSite и компоненты

- источники MetaCubeX, RunetFreedom, Loyalsoldier или собственные HTTPS-ссылки;
- ручное и периодическое обновление;
- отображение прогресса загрузки и проверки;
- атомарное применение с сохранением предыдущих файлов при ошибке;
- Android обновляет встроенный Mihomo вместе с APK;
- Server проверяет, устанавливает и откатывает отдельный бинарник Mihomo.

Статус Server: **реализовано**, системное расписание зависит от пакета ОС.

## 9.1. Обновление OrcheRoute

Android устанавливает подписанный APK через системный установщик. Linux Server
проверяет GitHub Release, SHA-256, имя пакета и архитектуру DEB, затем передаёт
установку отдельному root-helper. До изменения системы обязательны сохранённый
предыдущий DEB и резерв конфигурации. После `dpkg` helper проверяет control plane,
ранее активный transport и HTTP health; при ошибке устанавливает предыдущий DEB.
Успешный кандидат становится следующей точкой отката. Stable и beta выбираются
в общем интерфейсе, проверка новой версии запускается также автоматически.

## 10. API и WebUI

Android bridge и Server HTTP API используют одинаковые модели `status`, `pools`,
`nodes`, `subscriptions`, `operations`, `qualification`, `routes`, `network`,
`dns` и `components`. Server дополнительно предоставляет авторизацию, TLS,
публикацию WebUI в выбранные сети, журнал событий и системную диагностику.

Платформенные исключения не должны отображаться как сломанные элементы UI.
Длительная операция блокирует только конфликтующие действия, показывает этап,
прогресс и конкретную ошибку. Успешный статус закрывается автоматически; ошибка
остаётся до действия пользователя.

## Критерий полного паритета Server

Перенос завершён только когда одновременно выполнено следующее:

1. server monitor независимо и воспроизводимо различает три состояния сети;
2. контроллер не выполняет direct-пробы через VPN;
3. whitelist-список формируется, сохраняется, отменяется и восстанавливается;
4. CRUD подписок и серверов не запускает скрытые операции;
5. qualification и рейтинг дают одинаковый порядок кандидатов;
6. маршруты, DNS и интерфейсы сохраняются и реально применяются;
7. перезагрузка сохраняет намерение `enabled` и фактический lifecycle службы;
8. API-контракт и общий WebUI проходят локальные тесты Android и Server;
9. чистая серверная установка остаётся выключенной и готовой к настройке;
10. обновление пакета не стирает runtime.env, БД, подписки, маршруты и geo-файлы.
