# OrcheRoute API

> На 11.08.2026 контракт обслуживается production Go runtime на
> `127.0.0.1:19100`. Ответ `/v1/status` возвращает `runtime: "go"`; активный
> capture profile — `system`. Единственный control plane реализован на Go.

> Общий статус архитектуры, клиентов и production: [PROJECT_STATUS.md](PROJECT_STATUS.md).

Документ описывает локальный HTTP API бэкенда OrcheRoute, модель состояний,
управление подписками и политикой проверки серверов.

- Версия API: `1`
- Актуализировано: `2026-08-08`
- Реализация: `cmd/orcheroute-server` и `internal/serverruntime`

## Подключение и авторизация

- Базовый адрес на сервере: `http://127.0.0.1:19100`.
- API намеренно слушает только loopback-интерфейс и не доступен из локальной
  сети или интернета напрямую.
- Единственный публичный маршрут — `GET /healthz`.
- Для всех маршрутов `/v1/*` нужен заголовок:

  ```http
  Authorization: Bearer <api_token>
  ```

- Токен хранится на сервере в `/etc/orcheroute/runtime.env`, ключ `api_token`.
  Файл и токен нельзя публиковать, помещать в Git или вставлять в логи.
- Все ответы имеют `Content-Type: application/json; charset=utf-8` и
  `Cache-Control: no-store`.
- Максимальный размер JSON-тела запроса — 65 536 байт.

Пример локального запроса на сервере:

```bash
API_TOKEN="$(sudo sed -n 's/^api_token=//p' /etc/orcheroute/runtime.env)"
curl -sS \
  -H "Authorization: Bearer $API_TOKEN" \
  http://127.0.0.1:19100/v1/status
```

Для доступа с другого компьютера следует использовать SSH-туннель, не открывая
порт `19100` во внешнем firewall:

```bash
ssh -L 19100:127.0.0.1:19100 user@server
```

## WebUI

Серверный интерфейс состоит из статической React-сборки и встроенного Go-шлюза
`orcheroute-server`. Шлюз слушает HTTP `0.0.0.0:19110` и HTTPS
`0.0.0.0:19111`, но на уровне приложения принимает клиентов только из loopback
и сетей применённого списка `capture.management_cidrs`.

- доступ защищён HTTP Basic Authentication;
- API-токен читается шлюзом на сервере и не передаётся браузеру;
- изменяющие запросы требуют same-origin и заголовок `X-OrcheRoute-UI: 1`;
- имя пользователя и хеш пароля находятся в защищённом `runtime.env`;
- логин и пароль можно изменить в WebUI; пароль никогда не возвращается клиенту
  и сохраняется как PBKDF2-SHA256;
- список адресов панели строится из фактических адресов интерфейсов, входящих в
  применённые Management CIDR;
- для доверенного доступа можно по-прежнему использовать SSH-туннель:

  ```bash
  ssh -L 19110:127.0.0.1:19110 user@server
  ```

  После подключения открыть `http://127.0.0.1:19110`.

Настройки находятся в отдельном разделе WebUI **Доступ**. Поддерживаются три
режима TLS:

- `auto` — OrcheRoute один раз создаёт локальный CA и автоматически выпускает
  серверный сертификат с SAN для hostname и фактических IP устройства. CA можно
  скачать из интерфейса и добавить в доверенные сертификаты клиентского
  устройства. Серверный сертификат перевыпускается при изменении адресов;
- `custom` — используются абсолютные пути к готовому сертификату и закрытому
  ключу (ACME, корпоративный PKI или сертификат reverse proxy);
- `disabled` — HTTPS не запускается; режим предназначен для loopback или явно
  доверенной изолированной сети.

Режим хранится в `runtime.env`; основной systemd-unit не содержит домена или
путей Let's Encrypt. Изменение TLS перезапускает только WebUI-шлюз и не затрагивает
Mihomo, TUN, маршруты или выбранный VPN-сервер.

### `GET /api/v1/web/access`

Маршрут обслуживается WebUI-шлюзом, а не внутренним API. Возвращает текущий логин
без хеша пароля, применённые Management CIDR, подходящие адреса интерфейсов и
состояние HTTPS.

### `PUT /api/v1/web/access`

Изменяет Basic Auth или TLS WebUI. Требует текущую Basic-авторизацию, same-origin
и `X-OrcheRoute-UI: 1`.

```json
{"section":"credentials","username":"operator","password":"new-long-password"}
```

После успешного ответа браузер должен повторно пройти Basic Authentication уже
с новыми данными.

Пример включения переносимого локального CA:

```json
{"section":"tls","mode":"auto"}
```

Пример пользовательского сертификата:

```json
{"section":"tls","mode":"custom","cert_path":"/etc/ssl/router/fullchain.pem","key_path":"/etc/ssl/router/privkey.pem","certificate_name":"router.example.org"}
```

## Общая модель

В системе есть две агрегированные группы серверов:

| Группа | Приоритет | Назначение |
| --- | ---: | --- |
| `primary` | 0 | Основные подписки и предпочтительные серверы |
| `emergency` | 1 | Аварийные источники, используемые после исчерпания основной группы |

В каждую группу можно добавить несколько подписок. Каждая подписка разбирается
своим парсером, после чего ссылки всех включённых подписок группы объединяются и
дедуплицируются. Готовая группа проходит единый конвейер:

`TCP → URL-test → геолокация/исключения → 2 speed-test → порог скорости → стабильность`

Если обновить источник не удалось, его последний успешный кеш сохраняется. Новый
агрегированный provider записывается только при наличии как минимум одного
прошедшего квалификацию сервера.

## Проверка работоспособности

### `GET /healthz`

Не требует авторизации. Проверяет только доступность процесса API; это не тест
WAN или VPN.

```json
{"ok":true,"version":1}
```

## Состояние и наблюдение

### `GET /v1/status`

Возвращает состояние контроллера, WAN и выбранного прокси.

```json
{
  "version": 1,
  "timestamp": 1785697200,
  "updated_at": 1785697195,
  "stale": false,
  "connectivity": "proxy_ok",
  "wan": {
    "interface": "ppp0",
    "available": true
  },
  "network": {
    "capture_mode": "system",
    "direct_interface": "ppp0",
    "vpn_underlay_interface": "ppp0"
  },
  "service": {
    "enabled": true
  },
  "proxy": {
    "mode": "auto",
    "active_node": "PRIMARY-a1b2c3d4",
    "active_pool": "primary",
    "failure_streak": 0,
    "last_switch": 1785697000,
    "manual_until": 0
  }
}
```

`service.enabled` — состояние главного переключателя GUI. При выключении
останавливаются ядро Mihomo, контроллер и policy routing OrcheRoute, удаляются
его TUN `orcheroute0`, правила с приоритетами `9200..9299` и таблица `5353`.
API и WebUI остаются запущенными, поэтому панель доступна для повторного запуска.
Это освобождает системную маршрутизацию перед запуском другого VPN-клиента.
Сторонние TUN-интерфейсы, процессы Mihomo и их таблицы OrcheRoute не удаляет.

`stale=true` означает, что снимок контроллера не обновлялся более 45 секунд. В
этом случае `wan.available` возвращается как `null`.

Основные значения `connectivity`:

| Значение | Смысл |
| --- | --- |
| `starting` | Ещё нет актуального снимка |
| `proxy_ok` | Автоматический режим, активный прокси работает |
| `proxy_degraded` | Прокси работает нестабильно или переключение не удалось |
| `internet_down` | Недоступен сам интернет через чистый PPPoE |
| `recovery_grace` | WAN восстановился, действует защитная пауза |
| `manual_proxy_ok` | Узел, закреплённый вручную, работает |
| `manual_proxy_degraded` | Закреплённый вручную узел не проходит проверку |
| `manual_target_unavailable` | Указанный вручную узел недоступен |
| `controller_error` | Внутренняя ошибка цикла контроллера |

### `GET /v1/pools`

Сводка по двум группам из текущей конфигурации Mihomo.

```json
{
  "pools": [
    {"id":"primary","priority":0,"total":5,"alive":5,"selected":true},
    {"id":"emergency","priority":1,"total":8,"alive":7,"selected":false}
  ]
}
```

### `GET /v1/nodes`

Список узлов. Не содержит исходных URI, UUID, паролей или адресов подписок.

Необязательный фильтр: `?pool=primary` или `?pool=emergency`.

```json
{
  "nodes": [
    {
      "id": "PRIMARY-a1b2c3d4",
      "display_name": "Amsterdam · NL · 01",
      "pool": "primary",
      "priority": 0,
      "alive": true,
      "delay_ms": 184,
      "selected": true
    }
  ]
}
```

`id` — стабильный технический идентификатор для команд API. `display_name` —
исходное читаемое имя узла из подписки; оно не заменяется хешем в интерфейсе.

### `GET /v1/events?limit=100`

Последние события в обратном хронологическом порядке. `limit` приводится к
диапазону `1..500`, значение по умолчанию — `100`.

```json
{
  "events": [
    {
      "id": 42,
      "created_at": 1785697200,
      "event_type": "qualification_complete",
      "severity": "info",
      "from_node": null,
      "to_node": null,
      "pool": "primary",
      "reason": "subscription_aggregation",
      "details": {"sources":2,"fetched":23,"accepted":5,"rejected":0}
    }
  ]
}
```

### `GET /v1/policy`

Возвращает неизменяемые параметры автомата переключений:

```json
{
  "pool_priority": ["primary", "emergency"],
  "health_interval_seconds": 15,
  "failure_limit": 3,
  "cooldown_seconds": 900,
  "switch_retry_seconds": 60,
  "failback_probe_seconds": 60,
  "failback_stable_checks": 3,
  "max_candidates_per_incident": 3
}
```

### `GET /v1/operations`

Возвращает состояние длительных операций для WebUI. `subscription_update`
показывает получение подписок и квалификацию пулов, `network_apply` — применение
сетевого профиля, а `component_update` — загрузку геобаз и обновление ядра.

```json
{
  "subscription_update": {
    "status": "running",
    "phase": "url_test",
    "message": "URL-test 200/500",
    "current": 200,
    "total": 500,
    "pool": "primary",
    "updated_at": 1785699000,
    "active": true
  },
  "network_apply": {
    "status": "applied",
    "revision": 14,
    "rolled_back": false,
    "updated_at": 1785698983
  },
  "component_update": {
    "status": "idle",
    "phase": "idle",
    "updated_at": 0,
    "active": false
  }
}
```

Во время квалификации `phase` последовательно принимает значения `baseline`,
`tcp`, `url_test` и `speed_test`. `current/total` считаются по реально
завершённым проверкам, а не по расчётному таймеру. При полном отказе операция
возвращает конкретную причину в `message` и в `pools.<pool>.reason`, например
`all_servers_unavailable_tcp`, `all_servers_unavailable_url_test` или
`all_servers_failed_speed_or_stability`. Предыдущий рабочий provider при этом
не затирается.

## Компоненты и геобазы

### `GET /v1/components`

Возвращает установленную и последнюю проверенную версию Mihomo, флаг
`update_available`, время проверки, наличие, размер и время обновления
`GeoIP.dat`/`GeoSite.dat`, выбранный и фактически установленный источник,
настройку автоматического GEO-обновления и следующий запуск timer unit. Поле
`geo_sources` содержит доступные источники, а `catalog.geoip` и
`catalog.geosite` — реальные категории, прочитанные из установленных бинарных
баз. WebUI использует именно этот каталог, а не сгенерированный список.

### `PUT /v1/components/settings`

Сохраняет расписание отдельного `orcheroute-geo.timer`:

```json
{
  "geo_auto_update": true,
  "geo_interval_hours": 24,
  "geo_source": "runetfreedom"
}
```

Допустимые встроенные источники: `metacubex`, `runetfreedom` и
`loyalsoldier`. Для `geo_source: "custom"` обязательны прямые HTTPS-ссылки:

```json
{
  "geo_auto_update": true,
  "geo_interval_hours": 24,
  "geo_source": "custom",
  "geoip_url": "https://example.org/geoip.dat",
  "geosite_url": "https://example.org/geosite.dat"
}
```

Выбирается одна совместимая пара файлов: Mihomo одновременно использует один
`GeoIP.dat` и один `GeoSite.dat`. Сохранение меняет источник последующих
обновлений, но не подменяет работающие базы до явной или плановой GEO-операции.

Интервал допускается от 1 до 720 часов. Постоянный systemd timer просыпается раз
в час, а задача сравнивает возраст обеих геобаз с выбранным интервалом. До
наступления срока сеть не используется и файлы не скачиваются. При выключении
timer останавливается. Он запускает только GEO-операцию и никогда не обновляет
ядро автоматически.

### `POST /v1/components/update`

Запускает одну из операций `check`, `geo`, `core` или `all`:

```json
{"component":"geo"}
```

`check` обращается к официальному GitHub Releases API MetaCubeX, сохраняет
последний стабильный tag и подходящий release-asset, но ничего не устанавливает.

GEO-операция загружает обе базы выбранного источника, извлекает и проверяет их
каталоги, затем проверяет пару тестовой конфигурацией Mihomo. Только прошедшие
проверку файлы устанавливаются и становятся новым каталогом маршрутов.
Обновление ядра выполняет следующий цикл:

1. получает metadata официального stable release;
2. скачивает asset для архитектуры устройства и проверяет опубликованный SHA-256;
3. запускает новый бинарник отдельно и проверяет действующую конфигурацию;
4. сохраняет рабочий бинарник и атомарно устанавливает новый;
5. перезапускает ядро и контроллер, проверяет их версии и выполняет реальный
   HTTP-запрос через локальный SOCKS/VPN;
6. при любой ошибке восстанавливает сохранённый бинарник, перезапускает его и
   повторно проверяет VPN-трафик.

Если установленная версия уже совпадает с latest release, `core` завершается
успешно без перезапуска. Обновление ядра кратковременно прерывает VPN только при
фактической установке новой версии. Если OrcheRoute выключен, маршрут возвращает
`409 orcheroute_must_be_enabled`.

## Режим контроллера

### `POST /v1/service/enable`

Запускает policy routing, ядро Mihomo и контроллер. До запуска удаляет только
устаревшие правила и TUN OrcheRoute. Если выбран системный захват и уже активен
чужой TUN, возвращает `409 foreign_tun_active`, не меняя чужой VPN.

Ответ `202 Accepted`:

```json
{"accepted":true,"enabled":true}
```

### `POST /v1/service/disable`

Останавливает контроллер, Mihomo и policy routing OrcheRoute, затем удаляет его
TUN, правила и таблицы маршрутизации. API и WebUI продолжают работать. Команда
нужна в том числе перед запуском другого VPN на основе Mihomo.

Ответ `202 Accepted`:

```json
{"accepted":true,"enabled":false}
```

### `POST /v1/control/auto`

Возвращает контроллер в автоматический режим. Тело можно не передавать.
Основной пул имеет приоритет; если в нём нет доступных серверов, контроллер
выбирает аварийный. После восстановления устойчивого основного узла выполняется
автоматический возврат.

Ответ `202 Accepted`:

```json
{"accepted":true,"mode":"auto"}
```

### `POST /v1/control/emergency`

Включает режим «Только аварийный пул». Контроллер выбирает исключительно
доступные узлы группы `emergency`, не использует основной пул и не выполняет
автоматический возврат в него. Если готового аварийного узла пока нет,
контроллер сохраняет текущее соединение до окончания проверки, чтобы не
обрывать интернет намеренно.

При включении режима запускаются быстрый health-check Mihomo и полная проверка
сохранённых аварийных серверов без повторного скачивания подписок. Далее
контроллер удерживает выбранный узел до отказа и перебирает следующие доступные
узлы только внутри аварийного пула. Если кандидаты закончились, проверка
аварийного кеша запускается повторно. Потеря самого WAN замораживает
переключения, чтобы не помечать VPN-серверы неисправными при отсутствии обычного
интернета.

В интерфейсе это не отдельный основной режим, а включаемая опция рядом с
автоматическим/ручным выбором. Выключение опции возвращает `auto`.

```json
{"accepted":true,"mode":"emergency","check_scheduled":true}
```

### `POST /v1/control/manual`

Закрепляет конкретный узел. `node_id` нужно взять из `GET /v1/nodes`.

```json
{
  "node_id": "PRIMARY-a1b2c3d4",
  "lock_seconds": 3600
}
```

- `lock_seconds`: `60..86400` секунд.
- `0` означает ручной режим без срока завершения.
- Если поле не задано, используется `3600`.

Ответ `202 Accepted`:

```json
{
  "accepted": true,
  "mode": "manual",
  "node_id": "PRIMARY-a1b2c3d4",
  "manual_until": 1785700800
}
```

Запрос изменяет желаемое состояние. Фактическое переключение выполняет следующий
цикл контроллера; результат следует проверять через `GET /v1/status`.

## Подписки

### Модель подписки

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | string | Генерируется сервером, формат обычно `sub-<hex>` |
| `name` | string | Имя длиной `1..100` символов |
| `group` | string | `primary` или `emergency` |
| `parser` | string | `standard`, `inline` или `blacktemple` |
| `enabled` | boolean | Участвует ли источник в обновлениях |
| `interval_seconds` | integer | Интервал обновления `300..604800` секунд |
| `last_attempt` | Unix time | Последняя попытка загрузки, `0` если её не было |
| `last_success` | Unix time | Последнее успешное обновление |
| `last_status` | string | Обычно `pending`, `ok` или `error` |
| `last_error` | string/null | Тип последней ошибки без секретных подробностей |
| `last_links` | integer | Число ссылок при последнем успешном разборе |
| `created_at` | Unix time | Время создания |
| `updated_at` | Unix time | Время последнего изменения записи/статуса |
| `secret_configured` | boolean | Подтверждает наличие секрета |
| `builtin_default` | boolean | Входит ли источник во встроенный аварийный каталог |
| `description` | string | Описание встроенного источника; отсутствует у пользовательских |
| `repository` | string | Публичный репозиторий встроенного источника |

Поле `secret` принимается при создании или замене источника и не возвращается в
обычных GET-запросах. Получить его можно только отдельным явным действием
`POST /v1/subscriptions/{id}/secret`; это действие фиксируется в журнале.

Парсеры:

- `standard` — обычная HTTP/HTTPS-ссылка на подписку; загрузка и декодирование
  стандартного набора прокси-ссылок.
- `inline` — локальный многострочный список готовых URI `vless://`, `vmess://`,
  `trojan://`, `ss://`, `hysteria2://` и `hy2://`; сеть для получения источника
  не используется.
- `wireguard` — локальная конфигурация WireGuard или AmneziaWG в формате
  `[Interface]`/`[Peer]`. Поддерживаются несколько peer, IPv4/IPv6, DNS, MTU,
  PSK, keepalive и параметры AmneziaWG; приватный ключ остаётся секретом источника.
- `blacktemple` — специальный протокол получения подписки через установленный
  серверный helper.

### `GET /v1/subscriptions`

Возвращает все подписки без секретов.

```json
{
  "subscriptions": [
    {
      "id": "legacy-private",
      "name": "Legacy private",
      "group": "primary",
      "parser": "standard",
      "enabled": true,
      "interval_seconds": 900,
      "last_attempt": 1785697000,
      "last_success": 1785697000,
      "last_status": "ok",
      "last_error": null,
      "last_links": 4,
      "created_at": 1785690000,
      "updated_at": 1785697000,
      "secret_configured": true
    }
  ]
}
```

### `PUT /v1/subscriptions/default-emergency`

Атомарно сохраняет флажки встроенного аварийного каталога. В запросе передаются
только выбранные идентификаторы:

```json
{
  "enabled_ids": [
    "ebrasha-public",
    "default-au1rxx"
  ]
}
```

Источники, которых нет в `enabled_ids`, выключаются: updater не скачивает, не
парсит и не проверяет их серверы. Если набор изменился, аварийный пул
пересобирается один раз после сохранения всех флажков. Повторная отправка уже
действующего набора не запускает обновление.

Встроенные записи разрешено включать и выключать только этим методом (либо
обычным `PATCH` только с полем `enabled`). Их URL, парсер, группа и имя защищены
от изменения, а `DELETE` возвращает `409`.

### `POST /v1/subscriptions`

Добавляет подписку. Обязательны `name`, `group`, `parser`, `secret`.

```json
{
  "name": "Provider A",
  "group": "primary",
  "parser": "standard",
  "secret": "https://provider.example/subscription/token",
  "enabled": true,
  "interval_seconds": 900
}
```

Для `standard` значение `secret` обязано быть HTTP/HTTPS URL. Ответ —
`201 Created` с публичной моделью:

```json
{"subscription":{"id":"sub-a1b2c3d4e5f60708","name":"Provider A","group":"primary","parser":"standard","enabled":true,"interval_seconds":900,"last_attempt":0,"last_success":0,"last_status":"pending","last_error":null,"last_links":0,"created_at":1785697200,"updated_at":1785697200,"secret_configured":true}}
```

После создания обновление подписок запускается асинхронно.

Одинаковая пара `parser` + `secret` возвращает `409 duplicate_subscription`.
Для `inline` сервер нормализует URI, удаляет повторы внутри списка и URI,
которые уже находятся в другом локальном источнике. Число удалённых элементов
возвращается в `duplicates_removed`; полностью повторный список получает
`409 duplicate_servers`. Повторы между загружаемыми сетевыми подписками
удаляются агрегатором перед квалификацией.

### `POST /v1/subscriptions/import`

Пакетно принимает до 100 элементов в массиве `subscriptions`. Все записи
сначала проходят базовую валидацию; повторные источники и полностью повторные
локальные списки пропускаются, остальные сохраняются без автоматической
квалификации:

```json
{
  "subscriptions": [
    {"name":"A","group":"primary","parser":"standard","secret":"https://example.org/sub","enabled":true,"interval_seconds":900},
    {"name":"Local","group":"emergency","parser":"inline","secret":"vless://…\ntrojan://…","enabled":true,"interval_seconds":3600}
  ]
}
```

Ответ содержит массивы `created`, `skipped`, `refresh_scheduled: false` и
`refresh_required`. Проверка начинается только по явной кнопке «Обновить».

### `PATCH /v1/subscriptions/{id}`

Частично изменяет подписку. Разрешены поля:

`name`, `group`, `parser`, `secret`, `enabled`, `interval_seconds`.

Например, перенести подписку в аварийную группу:

```json
{"group":"emergency"}
```

Отключить источник без удаления:

```json
{"enabled":false}
```

Изменение только `name` или `interval_seconds` сохраняется без обновления и без
повторной квалификации стабильных пулов. При изменении `enabled`, `group`,
`parser` или `secret` перестраиваются только затронутые пулы. Кеш удаляется
только при изменении содержимого источника (`parser` или `secret`). Ответ
`200 OK` содержит публичную модель и флаг `refresh_scheduled`.

### `DELETE /v1/subscriptions/{id}`

Удаляет запись и её кеш, затем асинхронно запускает пересборку групп.

```json
{"deleted":true,"id":"sub-a1b2c3d4e5f60708"}
```

### `POST /v1/subscriptions/refresh`

Принудительно загружает все включённые подписки, но не запускает тестирование
серверов. Новые ссылки объединяются с сохранёнными с дедупликацией: сетевой
сбой, пустой ответ и неполная выдача источника не удаляют прежние серверы.
Ответ `202 Accepted` означает, что задача запущена, а не что работа завершилась.

```json
{"accepted":true}
```

### `POST /v1/subscriptions/{id}/refresh`

Принудительно загружает одну включённую подписку и объединяет результат с её
последним успешным кешем без проверки узлов.

### `POST /v1/subscriptions/check`

Проверяет и квалифицирует серверы из локальных кешей всех включённых подписок,
не обращаясь к их URL. Рабочие provider-файлы заменяются только если новый
результат содержит принятые узлы; при ошибке или нулевом результате продолжает
использоваться последний рабочий пул.

```json
{"accepted":true}
```

### `POST /v1/subscriptions/{id}/secret`

Возвращает действующую ссылку/секрет только по явному запросу пользователя:

```json
{"id":"sub-a1b2c3d4e5f60708","secret":"https://…","warning":"transport_must_be_trusted"}
```

Вызывать маршрут следует только через HTTPS или SSH-туннель. Значение не
попадает в события, обычное состояние панели или периодический polling.

### `POST /v1/subscriptions/{id}/export`

Возвращает секрет источника и исходные готовые URI из последнего успешного кеша:

```json
{
  "id": "sub-a1b2c3d4e5f60708",
  "name": "Provider A",
  "parser": "standard",
  "secret": "https://provider.example/subscription/token",
  "links": ["vless://…", "trojan://…"]
}
```

Маршрут предназначен для явного экспорта в буфер, файл или локально
сгенерированный QR-код. Как и `/secret`, его следует вызывать только через
HTTPS или доверенный локальный транспорт.

Updater защищён файловой блокировкой: параллельный запуск не создаёт второй
процесс. Таймер обновляет кеши источников по `interval_seconds`, но не заменяет
здоровый квалифицированный provider при каждом фоновом запуске. Полная
переквалификация выполняется вручную, после изменения состава подписок, при
отсутствии provider-файла или когда контроллер исчерпал рабочие узлы.

При сборке общего пула каждый узел сохраняет происхождение из конкретной
подписки. `GET /v1/nodes` возвращает для него `source_id` и `source_name`, а
WebUI показывает количество принятых серверов по источникам. Это не квота:
источник попадёт в рабочий пул только если хотя бы один его сервер пройдёт TCP,
URL, GeoIP, два speed-test и проверку стабильности. Воронка последнего запуска
берётся из `GET /v1/qualification`.

Если обновление уже выполняется или команда запуска уже записана, API отвечает
`409 subscription_update_in_progress`. Второй проход не ставится в очередь и не
запускается после первого. WebUI на это время блокирует действия, меняющие
состав подписок, и кнопки ручного обновления.

## Сетевые интерфейсы и режим захвата

Сетевой профиль отделяет назначение интерфейса от его технологии. Для API нет
разницы, является ли Linux-интерфейс Ethernet со статическим адресом, DHCP,
PPPoE, DSL, L2TP, WireGuard или другим L2/L3-устройством: важны имя интерфейса,
адрес и доступный gateway/default route.

В профиле две независимые исходящие роли:

| Роль | Назначение | Mark/table по умолчанию |
| --- | --- | --- |
| `direct` | Трафик списка `direct` и прямые DNS-запросы | `0x5351` / `5351` |
| `vpn_underlay` | Канал подключения OrcheRoute к VPN-серверам, их DNS и квалификация узлов | `0x5352` / `5352` |

В WebUI эта роль называется **«Канал к VPN-серверам»**. Имя `vpn_underlay`
сохраняется только в API и файлах профиля для обратной совместимости.

Роли могут использовать один интерфейс или разные. Например:

- `direct=enp2s0`, `vpn_underlay=enp3s0` — чистый интернет и транспорт VPN
  физически разделены;
- обе роли `ppp0` — текущая схема с одним PPPoE;
- `direct=enp2s0`, `vpn_underlay=wg0` — VPN-серверы достигаются через уже
  существующий WireGuard/L3-интерфейс.

Для каждой роли создаётся собственная policy-routing таблица. Поэтому выбор не
зависит от системного default route и продолжает работать, даже если default
смотрит в другой TUN/VPN. Custom outbound `DIRECT-EGRESS` привязан к роли
`direct`, а proxy-provider’ы и `VPN-UNDERLAY-DNS` — к `vpn_underlay`.

### Режимы захвата

Поле `capture.mode` поддерживает:

| Режим | Поведение |
| --- | --- |
| `interfaces` | TUN принимает трафик только из перечисленных LAN/ingress-интерфейсов |
| `system` | Общесистемный TUN для локального и маршрутизируемого трафика |

### Защита от DNS-утечек

При `dns_hijack=true` в режимах `interfaces` и `system` TUN перехватывает
обычные DNS-запросы как по UDP, так и по TCP на целевой порт 53. Не имеет
значения, какой DNS-сервер указал клиент: запрос к адресу провайдера, публичному
resolver или даже недоступному внешнему адресу принудительно передаётся
внутреннему DNS-модулю Mihomo.

Область защиты зависит от режима:

| Режим | Что защищено |
| --- | --- |
| `interfaces` | DNS устройств, приходящий с выбранных LAN/ingress-интерфейсов |
| `system` | DNS локальных приложений компьютера/сервера и маршрутизируемых через него клиентов |

`strict_route=true` дополняет перехват системными маршрутами и не позволяет
обычному резолверу обойти TUN через другой интерфейс. Внутренний DNS использует
`respect-rules`, поэтому результат отправляется через DNS-канал того же действия,
которое выбрала маршрутизация:

```text
приложение → UDP/TCP 53 → TUN → внутренний DNS
                                  ├─ direct → DNS direct → интерфейс direct
                                  └─ proxy  → DNS proxy  → выбранный VPN
```

Это предотвращает утечку обычного DNS при использовании OrcheRoute на
маршрутизаторе и на персональном компьютере, подключённом к интернету напрямую,
без NAT или трансляции LAN.

Граница защиты: DoH, DoQ и DoT уже являются зашифрованными соединениями, а не
пакетами UDP/TCP 53. Они рассматриваются как обычный трафик и следуют правилам
`block → direct → proxy`. DoT обычно можно направить или запретить правилом
`tcp:853`. DoH внешне является HTTPS на TCP/443, поэтому для выборочной обработки
нужно добавить домен или IP конкретного DoH-провайдера; глобальное правило
`tcp:443` затронет весь HTTPS. DoQ обычно использует UDP/853, но порт сервера
может отличаться.

#### Ограничения и безопасное применение TUN

В `interfaces` обязательно заполнить `capture.interfaces`. В `system` обязательно
задать хотя бы одну `management_cidrs`, чтобы SSH/управление можно было вывести из
перехвата. Применение `interfaces` или `system` требует отдельного явного
подтверждения.

При `bypass_local=true` автоматически исключаются:

- `lo`, loopback IPv4/IPv6;
- RFC1918, link-local, CGNAT, multicast и IPv6 ULA;
- адреса и подключённые подсети всех интерфейсов устройства;
- пользовательские `bypass_cidrs` и `management_cidrs`.

При выключенном IPv6 IPv6-подсети не передаются в `route-exclude-address` Mihomo.
Зарезервированный диапазон `240.0.0.0/4` также не добавляется автоматически,
поскольку Linux `auto-redirect` не может корректно принять такое исключение.
Собственный TUN использует таблицу `5353` и начальный индекс правил `9200`, не
пересекаясь со стандартными значениями `2022/9000` других реализаций.

Если уже существует другой TUN, включение нового системного захвата блокируется
ошибкой `foreign_tun_active`. OrcheRoute проверяет фактический конфликт сетевых
интерфейсов и правил, но не ищет, не запускает и не останавливает сторонние VPN-клиенты.
Перед включением OrcheRoute другой TUN необходимо отключить.

### Модель профиля

```json
{
  "version": 1,
  "revision": 2,
  "updated_at": 1785700000,
  "roles": {
    "direct": {
      "interface": "ppp0",
      "gateway": null,
      "source": null
    },
    "vpn_underlay": {
      "interface": "ppp0",
      "gateway": null,
      "source": null
    }
  },
  "capture": {
    "mode": "system",
    "interfaces": [],
    "bypass_local": true,
    "bypass_cidrs": [],
    "management_cidrs": ["192.168.0.0/16"],
    "dns_hijack": true,
    "strict_route": true
  }
}
```

`gateway=null` и `source=null` означают автоматический выбор из адресов и
маршрутов выбранного интерфейса. Для интерфейса без собственного default route
можно явно задать IPv4 gateway и source address.

### `GET /v1/network/interfaces`

Возвращает обнаруженную топологию:

- имя, тип, state и MTU каждого интерфейса;
- IPv4/IPv6-адреса;
- default routes, gateway, metric и таблицу;
- рассчитанный список локальных CIDR для безопасного bypass.

Этот метод только читает состояние и ничего не применяет.

На Android endpoint возвращает доступность `auto`, Wi-Fi, мобильной сети и
Ethernet, а также адреса активных `Network`. Имена Linux-интерфейсов в мобильном
профиле не используются: выбранная сеть передаётся обычному
`VpnService.setUnderlyingNetworks`, поэтому root не требуется.

### `GET /v1/network/profile`

Возвращает:

- `desired` — сохранённый желаемый профиль;
- `active` — фактически применённый профиль;
- `in_sync` — совпадают ли они;
- `apply` — состояние последнего применения: `never`, `applying`, `applied`,
  `blocked` или `failed`.

Секретов в профиле нет.

### `POST /v1/network/validate`

Проверяет профиль без сохранения и изменения сети:

```json
{"profile":{"version":1,"roles":{"direct":{"interface":"enp2s0","gateway":"192.0.2.1","source":"192.0.2.2"},"vpn_underlay":{"interface":"enp3s0","gateway":"198.51.100.1","source":"198.51.100.2"}},"capture":{"mode":"interfaces","interfaces":["enp10s0f1"],"bypass_local":true,"bypass_cidrs":[],"management_cidrs":[],"dns_hijack":true,"strict_route":true}}}
```

Ответ содержит нормализованный `profile`, `resolved_roles`, итоговый
`effective_bypass_cidrs`, предупреждения, digest и признак необходимости
подтверждения. Неработающий интерфейс возвращается как warning; отсутствующий или
некорректный интерфейс — как ошибка.

### `PUT /v1/network/profile`

Сохраняет профиль как `desired`, но не меняет действующую сеть. Используется
optimistic locking по ревизии:

```json
{
  "revision": 2,
  "profile": {
    "version": 1,
    "roles": {
      "direct": {"interface":"enp2s0","gateway":null,"source":null},
      "vpn_underlay": {"interface":"enp3s0","gateway":null,"source":null}
    },
    "capture": {
      "mode":"system",
      "interfaces":[],
      "bypass_local":true,
      "bypass_cidrs":[],
      "management_cidrs":["192.168.0.0/16"],
      "dns_hijack":true,
      "strict_route":true
    }
  }
}
```

Ответ сообщает `applied:false`. При устаревшей ревизии возвращается `409` с
`network_revision_conflict`.

### `POST /v1/network/apply`

Асинхронно применяет уже сохранённую desired-ревизию:

```json
{"revision":3}
```

Для `interfaces` и `system` требуется:

```json
{"revision":3,"confirm_system_capture":true}
```

Ответ `202` означает только запуск транзакции. Фактический результат нужно
проверять через `GET /v1/network/profile`.

На Android применяется сохранённый transport и DNS. Если VPN уже включён,
служба пересоздаёт TUN/Mihomo и фиксирует `applied` только после успешного
подключения; если VPN выключен, профиль становится активным для следующего
запуска. Недоступный явно выбранный transport возвращает ошибку вместо
молчаливого перехода на другую сеть.

Транзакция:

1. Разрешает gateway/source и создаёт отдельные route table и fwmark для ролей.
2. Генерирует и проверяет конфигурацию Mihomo.
3. Перезапускает сетевое ядро Mihomo и контроллер; API и WebUI остаются доступны
   для наблюдения за операцией.
4. Проверяет обе исходящие роли и реальный HTTP через прокси.
5. Только после успеха фиксирует профиль как active.

При любой ошибке восстанавливаются предыдущие policy routes, конфигурация и
active-профиль. Поле `apply.error` содержит только безопасный код/тип ошибки.
Пока задача имеет статус `queued` или `applying`, повторный запрос возвращает
`409 network_apply_in_progress`. Статусы `failed`, `blocked` и `applied`
завершают ожидание WebUI; потерянная systemd-задача переводится в
`network_apply_interrupted`, поэтому бессрочного состояния «выполняется» нет.

## DNS-профиль

DNS входит в ревизионный сетевой профиль, но имеет отдельные API-методы для
простого GUI. Запросы разделены на три канала:

| Канал | Что разрешает | Как отправляется |
| --- | --- | --- |
| `direct` | Домены, выбранные списком `direct` | Через `DIRECT-EGRESS` и интерфейс роли `direct` |
| `proxy` | Домены списка `proxy` и всё, попавшее в VPN по умолчанию | Через выбранный `ACTIVE` VPN |
| `vpn_underlay` | Доменные имена самих VPN-серверов | Через `VPN-UNDERLAY-DNS` и интерфейс роли `vpn_underlay` |

Разделение не позволяет адресу VPN-сервера разрешаться через ещё не поднятый VPN
и одновременно предотвращает прямую DNS-утечку для обычного proxy-трафика.

### Модель DNS

```json
{
  "direct": ["1.1.1.1", "8.8.8.8"],
  "proxy": [
    "https://1.1.1.1/dns-query",
    "https://8.8.8.8/dns-query"
  ],
  "vpn_underlay": ["1.1.1.1", "8.8.8.8"],
  "bootstrap": ["1.1.1.1", "8.8.8.8"],
  "cache_algorithm": "arc",
  "prefer_h3": false,
  "use_hosts": true,
  "ipv6": false
}
```

Поддерживаемые resolver’ы:

- UDP: `1.1.1.1`, `udp://1.1.1.1`;
- TCP: `tcp://8.8.8.8`;
- DNS-over-TLS: `tls://1.1.1.1`;
- DNS-over-HTTPS: `https://cloudflare-dns.com/dns-query`;
- DNS-over-QUIC: `quic://dns.adguard.com:784`.

На каждый канал разрешено `1..8` серверов. `bootstrap` также содержит `1..8`
значений, но только буквальные IPv4-адреса: он нужен для разрешения hostname
самих DoH/DoT/DoQ-серверов.

Пользователь не может дописывать `#proxy` или `#interface` в resolver: API
добавляет безопасную привязку самостоятельно. Логин, пароль и URL fragment также
запрещены. `cache_algorithm` принимает `lru` или `arc`.

IPv6 DNS пока должен оставаться `false`, поскольку активная egress-модель
проверена только для IPv4. Попытка включения возвращает
`ipv6_dns_not_enabled`.

### `GET /v1/dns`

Возвращает:

- `desired` и `active` DNS-конфигурации;
- `in_sync`;
- `network_revision`, общую с сетевым профилем;
- статус последнего применения.

### `POST /v1/dns/validate`

Проверяет DNS-конфигурацию без сохранения:

```json
{
  "dns": {
    "direct": ["9.9.9.9"],
    "proxy": ["https://dns.quad9.net/dns-query"],
    "vpn_underlay": ["9.9.9.9"],
    "bootstrap": ["9.9.9.9"],
    "cache_algorithm": "arc",
    "prefer_h3": false,
    "use_hosts": true,
    "ipv6": false
  }
}
```

Ответ содержит нормализованный `config` и `effective`, где видны автоматически
добавленные `#DIRECT-EGRESS`, `#ACTIVE` и `#VPN-UNDERLAY-DNS`.

### `PUT /v1/dns`

Сохраняет DNS как часть desired-профиля и увеличивает общую network revision:

```json
{
  "revision": 6,
  "dns": {
    "direct": ["9.9.9.9"],
    "proxy": ["https://dns.quad9.net/dns-query"],
    "vpn_underlay": ["9.9.9.9"],
```

Ответ содержит `applied:false` и новый `network_revision`. Для фактического

```http

```


системного захвата.

## Маршрутизация

Маршрутизация представлена тремя простыми списками. Они проверяются сверху вниз
в фиксированном порядке:

| Список | Действие Mihomo | Назначение |
| --- | --- | --- |
| `block` | `REJECT` | Запретить соединение |
| `direct` | `DIRECT` | Отправить напрямую через чистый PPPoE, минуя VPN |
| `proxy` | `ACTIVE` | Отправить через выбранный VPN-сервер |

Если адрес попадает сразу в несколько списков, побеждает список, расположенный
выше: `block → direct → proxy`. Поле `default` задаёт действие для трафика,
который не совпал ни с одним правилом: `proxy`, `direct` или `block`. В Mihomo
оно реализовано скрытым селектором `DEFAULT`, поэтому меняется без перезапуска
ядра.

### Формат элементов

Каждый список можно передать массивом строк или одной многострочной строкой.
Пустые строки и строки, начинающиеся с `#`, игнорируются. Комментарии не
сохраняются: API возвращает нормализованные значения.

| Ввод | Тип | Результат |
| --- | --- | --- |
| `10.2.3.4` | Отдельный IP | `IP-CIDR,10.2.3.4/32` |
| `10.0.1.7/23` | CIDR | Нормализуется в `IP-CIDR,10.0.0.0/23` |
| `10.0.0.0-11.0.0.0` | Включительный IP-диапазон | Минимальный набор CIDR без перебора адресов |
| `example.com` | Доменный суффикс | `example.com` и все его поддомены |
| `=example.com` | Точный домен | Только `example.com` |
| `.example.com` | Явный доменный суффикс | `example.com` и его поддомены |
| `*.ru` | Доменная маска | Все имена, соответствующие окончанию `.ru` |
| `*yandex.ru` | Доменная маска | `yandex.ru`, `apt.yandex.ru`, `hello-yandex.ru` и другие совпадения |

Обычный домен намеренно имеет суффиксную семантику: правило `vk.com` также
совпадает с `queuev4.vk.com`. Это устраняет неполное срабатывание списков после
DNS-перехвата или определения имени снифером. Префикс `=` оставляет точное
совпадение.

В масках поддерживаются `*` — ноль или больше символов и `?` — ровно один
символ. Маски компилируются в `DOMAIN-WILDCARD`, поэтому `*` может пересекать
уровни домена. Unicode-домены без масок преобразуются в Punycode автоматически;
Unicode вместе с `*` или `?` нужно передавать уже в Punycode.

Ведущая маска имеет семантику суффикса: `*.ru`, `*2ip.ru` и `.2ip.ru`
компилируются в `DOMAIN-SUFFIX` и совпадают как с корневым доменом, так и с его
поддоменами. Маска внутри имени, например `api-*.example.org`, остаётся
`DOMAIN-WILDCARD`.

#### GeoIP и GeoSite

В любом списке поддерживаются элементы `geoip:<код>` и `geosite:<набор>`:

```text
geoip:RU
geosite:category-ads-all
geosite:youtube
```

Они компилируются соответственно в `GEOIP,RU` и `GEOSITE,<набор>`. Доступные
значения WebUI получает из реально установленной пары `GeoIP.dat` и
`GeoSite.dat`. Источник и период обновления выбираются пользователем; базы также
можно обновить вручную через API компонентов.

#### Порты и транспортные протоколы

Правило с ведущим двоеточием описывает целевой порт независимо от транспортного
протокола. TCP и UDP можно выбирать отдельными правилами для всего протокола.
Старые комбинированные записи `tcp:443`/`udp:53` продолжают поддерживаться как
расширенный синтаксис.

WebUI также предлагает пресеты `preset:<тип>`: `http`, `https`, `quic`, `dns`,
`dot`, `doq`, `ssh`, `ftp`, `mail`, `torrent`, `ntp`, `stun`, `rdp`, `openvpn`
и `wireguard`. Они компилируются в комбинации TCP/UDP и типовых портов. Это не
глубокое распознавание приложений: например, `preset:torrent` покрывает
TCP/UDP `6881-6889`, но клиент BitTorrent со случайным портом может его обойти.

| Ввод | Нормализованное значение | Совпадение |
| --- | --- | --- |
| `:5000` | `:5000` | Любой протокол на целевой порт 5000 |
| `:5000-6000` | `:5000-6000` | Любой протокол на диапазон 5000–6000 |
| `:5000,5002,5005` | без изменений | Любой протокол на три перечисленных порта |
| `tcp:443` | `tcp:443` | TCP на целевой порт 443 |
| `udp:53` | `udp:53` | UDP на целевой порт 53 |
| `53/udp` | `udp:53` | Альтернативная запись UDP/53 |
| `any:80,443` | `:80,443` | Совместимая старая запись; нормализуется в новый формат |
| `tcp:80,443,8000-8999` | без изменений | Несколько портов и диапазонов в одном элементе |
| `udp:*` | `udp:*` | Весь UDP-трафик независимо от порта |
| `tcp:*` | `tcp:*` | Весь TCP-трафик независимо от порта |

Одиночные порты должны находиться в диапазоне `1..65535`. Для диапазона начало
не может быть больше конца. `any:*` запрещён, поскольку он совпал бы вообще со
всем трафиком и скрыл бы расположенные ниже списки; для такого поведения следует
использовать финальную политику маршрутизации.

Комбинация протокола и порта компилируется в логическое правило Mihomo `AND`:

```text
tcp:443  → AND,((NETWORK,TCP),(DST-PORT,443))
udp:53   → AND,((NETWORK,UDP),(DST-PORT,53))
:443     → DST-PORT,443
udp:*    → NETWORK,UDP
```

Правило можно поместить в любой из трёх списков. Например:

```json
{
  "default": "proxy",
  "lists": {
    "direct": ["*.ru", ":123"],
    "proxy": [":443"],
    "block": ["tcp:25", "udp:1900"]
  }
}
```

В этом примере российские домены и порт NTP идут напрямую, HTTPS/QUIC — через VPN,
а исходящий SMTP/25 и SSDP/1900 блокируются. При этом сохраняется глобальный
приоритет списков `block → direct → proxy`: например, `tcp:25` из `block`
победит более широкое `tcp:*` из `direct`.

Поддерживаются IPv4 и IPv6. Начало и конец диапазона должны иметь одну версию IP,
а начало не может быть больше конца. IP-правила применяются и к назначениям,
полученным после DNS-разрешения.

Ограничения: до 10 000 исходных элементов на список и до 512 символов на элемент.
Повторы внутри одного списка удаляются с сохранением исходного порядка.

### `GET /v1/routes`

Возвращает текущую ревизию, `default`, три нормализованных списка и статистику
компиляции.

```json
{
  "version": 1,
  "revision": 3,
  "updated_at": 1785698000,
  "precedence": ["block", "direct", "proxy"],
  "lists": {
    "direct": ["*.ru", "10.0.0.0/23"],
    "proxy": ["example.com"],
    "block": ["*yandex.ru"]
  },
  "stats": {
    "direct": {
      "source_entries": 2,
      "normalized_entries": 2,
      "compiled_rules": 2,
      "duplicates_removed": 0,
      "ranges": 0
    },
    "proxy": {
      "source_entries": 1,
      "normalized_entries": 1,
      "compiled_rules": 1,
      "duplicates_removed": 0,
      "ranges": 0
    },
    "block": {
      "source_entries": 1,
      "normalized_entries": 1,
      "compiled_rules": 1,
      "duplicates_removed": 0,
      "ranges": 0
    }
  }
}
```

### `POST /v1/routes/validate`

Проверяет и компилирует списки, ничего не сохраняя и не применяя. Этот маршрут
предназначен в том числе для предварительной проверки в GUI.

```json
{
  "lists": {
    "direct": ["10.0.0.0-11.0.0.0", "*.ru"],
    "proxy": ["example.com"],
    "block": ["*yandex.ru"]
  }
}
```

Успешный ответ содержит `valid`, `precedence`, `normalized`, `compiled`, `items`
и `stats`. В `items` для каждой исходной записи возвращаются:

- `source` — полученная строка;
- `kind` — `ip`, `cidr`, `ip_range`, `domain`, `port`, `transport` или `protocol`;
- `normalized` — каноническое значение;
- `rules` — созданные правила Mihomo.

Пример ошибки с точной позицией для подсветки поля в GUI:

```json
{
  "error": "invalid_ip_range",
  "list": "direct",
  "index": 0,
  "entry": "10.0.0.5-foo"
}
```

`index` отсчитывается с нуля в переданном массиве.

Ошибки транспортных правил:

| Код | Причина |
| --- | --- |
| `invalid_port` | Порт не является числом `1..65535` |
| `invalid_port_range` | Некорректная граница диапазона или начало больше конца |
| `invalid_port_rule` | Неизвестный протокол, пустой список портов, неверная форма или запрещённый `any:*` |

### `PUT /v1/routes`

Атомарно заменяет сразу все три списка и обновляет живые rule-provider’ы Mihomo.
Для защиты от потери параллельных изменений GUI должен отправлять номер ревизии,
полученный через `GET /v1/routes`:

```json
{
  "revision": 3,
  "default": "direct",
  "lists": {
    "direct": ["*.ru", "10.0.0.0/23"],
    "proxy": ["example.com"],
    "block": ["*yandex.ru"]
  }
}
```

Если ревизия уже изменилась, API отвечает `409`:

```json
{"error":"route_revision_conflict"}
```

В этом случае клиент должен заново получить `GET /v1/routes`, показать конфликт
пользователю и не повторять перезапись автоматически. Поле `revision` технически
можно опустить, но для GUI это не рекомендуется.

При успехе provider-файлы обновляются без перезапуска Mihomo:

```json
{
  "updated": true,
  "routes": {
    "version": 1,
    "revision": 4,
    "updated_at": 1785698100,
    "default": "direct",
    "precedence": ["block", "direct", "proxy"],
    "lists": {
      "direct": ["*.ru", "10.0.0.0/23"],
      "proxy": ["example.com"],
      "block": ["*yandex.ru"]
    },
    "stats": {}
  }
}
```

Если Mihomo не смог перечитать хотя бы один provider, API восстанавливает
предыдущие списки и provider-файлы и отвечает `503`.

## Политика квалификации

### `GET /v1/qualification`

Возвращает:

- `policy` — сохранённые общие значения и настройки групп;
- `effective` — итоговые настройки каждой группы после наследования;
- `reports` — отчёт последнего прогона для `primary` и `emergency`, либо `null`,
  если группа ещё не проверялась.

Поля отчёта включают `input`, `tcp_alive`, `url_alive`, `speed_tested`,
`qualified`, `retained`, исключённые страны, измеренную скорость WAN
`baseline_mbps`, рассчитанный порог `threshold_mbps`, его источник
`threshold_source`, коэффициент стабильности и распределение причин отбраковки
в `outcomes`.

Перед квалификацией выполняется прямой speed-test через WAN-интерфейс. Порог
прохождения равен 10% от измеренной скорости WAN. Значение `min_speed_mbps`
используется только как резервный порог, если прямой замер не удался. Результат
прямого замера кешируется на 10 минут, поэтому при последовательной проверке
основного и аварийного пулов канал не измеряется повторно. Одновременно
проверяются не более шести серверов; два замера одного сервера идут последовательно.

В Android объём каждого замера выбирается по измеренной скорости линии: примерно
полсекунды передачи, но не меньше 256 КиБ и не больше 2 МиБ. Фиксированный файл
10 МиБ не используется. Для аварийного пула после URL-test отбираются лучшие
серверы отдельно из каждой подписки, и только они переходят к speed-test.

Перед проверкой Android сопоставляет два настраиваемых URL: ресурс, доступный при
белых списках, и ресурс обычного открытого Интернета. Если доступны оба, режим
считается обычным; если только первый — режимом белых списков; если ни один —
отсутствием Интернета. При полном отсутствии Интернета сохранённые статусы
серверов не затираются, а при белых списках недоступный speed-test пропускается.

URL-test использует три независимых адреса Google, Cloudflare и Microsoft. Сервер
переходит к speed-test, если успешны как минимум два из трёх запросов.

### `PUT /v1/qualification/policy`

Частично обновляет политику. Изменения начинают действовать при следующей
пересборке provider-файлов.

Пример изменения общих требований:

```json
{
  "defaults": {
    "excluded_countries": ["RU", "BY"],
    "min_speed_mbps": 20,
    "stability_ratio": 0.7,
    "tcp_timeout_ms": 2000,
    "url_timeout_ms": 3000,
    "geo_timeout_ms": 5000,
    "speed_timeout_ms": 15000,
    "allowlist_probe_url": "https://ya.ru/",
    "open_internet_probe_url": "https://www.cloudflare.com/cdn-cgi/trace"
  }
}
```

Пример ограничения объёма проверки аварийной группы:

```json
{
  "pools": {
    "emergency": {
      "url_limit": 1200,
      "speed_candidates": 60,
      "speed_candidates_per_source": 100,
      "keep": 20
    }
  }
}
```

Ограничения:

| Поле | Допустимое значение |
| --- | --- |
| `excluded_countries` | До 64 кодов ISO alpha-2, например `RU` |
| `min_speed_mbps` | `0.1..10000`; резервный порог при ошибке замера WAN |
| `stability_ratio` | `0.1..1.0` |
| `tcp_timeout_ms` | `500..10000`; ожидание TCP-проверки одного сервера |
| `url_timeout_ms` | `1000..30000`; ожидание одного URL-test через сервер |
| `geo_timeout_ms` | `1000..15000`; ожидание определения региона сервера |
| `speed_timeout_ms` | `5000..120000`; ожидание одного замера скорости |
| `allowlist_probe_url` | HTTP(S)-адрес, гарантированно доступный при белых списках |
| `open_internet_probe_url` | HTTP(S)-адрес, доступный в обычном открытом Интернете |
| `url_limit` | `0..10000`; `0` — без лимита |
| `speed_candidates` | `0..10000`; `0` — все прошедшие URL-test |
| `speed_candidates_per_source` | `0..10000`; максимум кандидатов на speed-test из каждой подписки, `0` — без лимита |
| `keep` | `0..10000`; `0` — сохранить всех прошедших |

Настройки `excluded_countries`, `min_speed_mbps` и `stability_ratio` можно также
задать внутри конкретной группы. `null` в переопределении означает наследование
значения из `defaults`.

Текущая политика по умолчанию:

```json
{
  "version": 1,
  "defaults": {
    "excluded_countries": [],
    "min_speed_mbps": 10.0,
    "stability_ratio": 0.65,
    "tcp_timeout_ms": 2000,
    "url_timeout_ms": 3000,
    "geo_timeout_ms": 5000,
    "speed_timeout_ms": 15000,
    "allowlist_probe_url": "https://ya.ru/",
    "open_internet_probe_url": "https://www.cloudflare.com/cdn-cgi/trace"
  },
  "pools": {
    "primary": {"url_limit":0,"speed_candidates":0,"speed_candidates_per_source":0,"keep":0},
    "emergency": {"url_limit":1200,"speed_candidates":60,"speed_candidates_per_source":100,"keep":20}
  }
}
```

## Коды ответов и ошибки

| HTTP | Значение |
| ---: | --- |
| `200` | Запрос выполнен |
| `201` | Подписка создана |
| `202` | Команда принята и будет обработана контроллером/systemd |
| `400` | Ошибка JSON, валидации, неизвестный узел или неверный диапазон |
| `401` | Нет корректного Bearer-токена |
| `404` | Маршрут или подписка не найдены |
| `409` | Конфликт ревизии/операции, выключенный OrcheRoute или активный чужой TUN |
| `503` | Недоступен Mihomo, БД или другой внутренний компонент |

Формат ошибки:

```json
{"error":"unauthorized"}
```

Для внутренних сбоев дополнительно возвращается безопасное имя типа исключения:

```json
{"error":"backend_unavailable","type":"URLError"}
```

## Примеры `curl`

Во всех примерах предполагается, что переменная `API_TOKEN` уже установлена.

```bash
API=http://127.0.0.1:19100
AUTH="Authorization: Bearer $API_TOKEN"

# Статус
curl -sS -H "$AUTH" "$API/v1/status"

# Основные узлы
curl -sS -H "$AUTH" "$API/v1/nodes?pool=primary"

# Добавление аварийной подписки
curl -sS -X POST -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"name":"Fallback B","group":"emergency","parser":"standard","secret":"https://example.invalid/sub","interval_seconds":3600}' \
  "$API/v1/subscriptions"

# Принудительно запросить запуск updater
curl -sS -X POST -H "$AUTH" "$API/v1/subscriptions/refresh"

# Обновить одну подписку
curl -sS -X POST -H "$AUTH" "$API/v1/subscriptions/sub-a1b2/refresh"

# Обновить GeoIP и GeoSite
curl -sS -X POST -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"component":"geo"}' "$API/v1/components/update"

# Вернуть автоматическое управление
curl -sS -X POST -H "$AUTH" "$API/v1/control/auto"

# Проверить списки маршрутизации без сохранения
curl -sS -X POST -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"lists":{"direct":["*.ru","udp:123"],"proxy":["tcp:443","udp:443"],"block":["*yandex.ru","tcp:25"]}}' \
  "$API/v1/routes/validate"

# Получить текущие списки и номер ревизии
curl -sS -H "$AUTH" "$API/v1/routes"

# Обнаружить сетевые интерфейсы и маршруты
curl -sS -H "$AUTH" "$API/v1/network/interfaces"

# Получить desired/active сетевой профиль и статус применения
curl -sS -H "$AUTH" "$API/v1/network/profile"

# Получить DNS direct/proxy/vpn_underlay
curl -sS -H "$AUTH" "$API/v1/dns"
```

## Режим белых списков операторов

Модель производного пула общая для всех runtime-ов и находится в Go-пакете
`internal/whitelist`. Android получает её через `mobilecore`, Linux/Windows
server используют напрямую, а Desktop — через локальный серверный bridge.
Платформенный код только выполняет сетевую проверку и запускает выбранный узел.

Переходы автомата: `begin`, `add_source`/`replace_source`, `request`, `confirm`,
`fail`, `complete`, `deactivate`. После `request` выбранный узел сохраняется как
`pending_node`: повторный или параллельный запрос возвращает тот же узел и не
переключает систему, пока адаптер явно не передаст `confirm` либо `fail`.
При `fail` нерабочий узел удаляется, и только затем выбирается следующий.
Замена результатов одной подписки не затрагивает узлы остальных источников.

Клиент различает обычный Интернет, ограниченную сеть оператора и полное
отсутствие WAN двумя независимыми контрольными адресами. Переход в ограниченную
сеть является отдельным состоянием, а не отказом текущего прокси.

При переходе в режим белых списков клиент:

1. Проверяет все сохранённые серверы включённых подписок основного и аварийного
   пулов (`TCP -> URL-test`). Обновлять или скачивать подписки для этого не
   требуется.
2. Не применяет `excluded_countries`: в ограниченной сети доступность важнее
   обычного предпочтения региона.
3. Подключается к первому подтвердившему работу серверу, не дожидаясь окончания
   полного сканирования; проверка остальных серверов продолжается в фоне.
4. Временно устанавливает действие по умолчанию `proxy`, очищает временные
   `direct` и `proxy`-исключения и сохраняет только пользовательский список
   `block`.
5. После восстановления обычного Интернета возвращает сохранённую
   маршрутизацию и обычную страновую фильтрацию.

Рабочие узлы сохраняются в отдельном производном пуле `whitelist`. Первый
подтвердивший работу узел может быть включён немедленно, однако проверка всех
остальных кандидатов продолжается. При отказе активный узел удаляется из этого
пула и выбирается следующий. Когда первоначальный пул готов и соединение
работает, клиент последовательно обновляет включённые подписки. Изменившиеся
наборы проходят повторную проверку, после чего атомарно заменяется только часть
whitelist-пула, принадлежащая соответствующему источнику.

Если после полного прохода пул `whitelist` пуст, VPN останавливается, системный
профиль закрывается, а состояние содержит явную ошибку об отсутствии доступных
серверов. Основной и аварийный пулы при этом не перезаписываются.

Обнаружение кандидата и подтверждение подключения являются разными состояниями.
Пока Mihomo не запустил TUN, следующий пакет проверки не считает соединение
готовым. Если первый кандидат не запускается, он исключается, а любой следующий
найденный узел немедленно инициирует новую попытку. Одновременно допускается
только одна попытка запуска, поэтому параллельные результаты URL-test не создают
гонку перезапусков.

### `POST /v1/subscriptions/{id}/check`

Проверяет только сохранённые серверы выбранной подписки, не скачивая её заново и
не запуская обработку остальных источников. В режиме белых списков атомарно
обновляется только принадлежащая этой подписке часть пула `whitelist`.

Списки доступных при ограничениях доменов и IP могут использоваться как
дополнительные обновляемые источники, но не заменяют живую проверку: фактический
набор зависит от оператора, региона, вышки и MVNO, а фильтрация может одновременно
учитывать IP и SNI.
| Исходные списки маршрутов | `/var/lib/orcheroute/routes.json` |
| Скомпилированные правила | `/var/lib/orcheroute/rules/direct.txt`, `proxy.txt`, `block.txt` |
| Желаемый сетевой профиль | `/var/lib/orcheroute/network-profile.json` |
| Активный сетевой профиль | `/var/lib/orcheroute/network-active.json` |
| Статус применения сети | `/var/lib/orcheroute/network-apply-status.json` |

| Геобазы | `/var/lib/orcheroute/GeoIP.dat`, `/var/lib/orcheroute/GeoSite.dat` |

## Важные эксплуатационные правила

1. Не публиковать порт `19100` и не помещать `runtime.env` в резервные копии без
   шифрования.
2. После команд с ответом `202` проверять фактический результат отдельным GET.
3. Перед удалением последней рабочей подписки группы сначала добавить и проверить
   замену.
4. Не считать `/healthz` подтверждением работоспособности WAN или VPN — для этого
   нужен `/v1/status`.
5. OrcheRoute не управляет сторонними VPN-клиентами. Перед применением режима
   `interfaces` или `system` пользователь самостоятельно освобождает конфликтующий
   TUN; при неудачной проверке OrcheRoute возвращает собственный предыдущий профиль.
